# Kuxmate engineering foundation

**Research date:** 2026-09-20
**Scope:** repository foundation only; no product features, domain tables, seed data, authentication flows, or forum behavior are included.

The starting repository contained only `README.md` and the project `AGPL-3.0` license. This document records the smallest foundation that gives the project clear boundaries without committing to infrastructure that is not needed yet.

## Decisions

| Area | Decision | Why this fits Kuxmate | Deferred or rejected alternatives |
| --- | --- | --- | --- |
| Runtime and package manager | Node.js 22.12+ and pnpm 12.5.1 workspaces | Current LTS-compatible baseline, native web APIs, reproducible lockfile, and efficient workspace installs | No Nx/Turborepo: two applications and one package do not justify another orchestration layer |
| Frontend | Next.js 16 App Router with React 19 and TypeScript | Server rendering, streaming, metadata, nested layouts, and static or dynamic rendering support public, crawlable pages while keeping client JavaScript deliberate; the Node standalone output is self-hostable | React Router framework mode remains a credible web-standards-first option; Astro is stronger for content-only sites, not a forum application with substantial interaction |
| Backend | Fastify 5 as a separate TypeScript HTTP process | High-throughput HTTP, a small plugin model, JSON Schema validation/serialization, and built-in Pino logging; it can scale independently from the web renderer | NestJS adds a useful opinionated container but also adds decorators/modules and more framework surface than the initial platform needs; Hono is attractive for edge runtimes but is not the best default for a Node/PostgreSQL service |
| Primary database | PostgreSQL 18, with PostgreSQL 16+ as the compatibility floor unless a feature requires newer SQL | Mature relational constraints and transactions suit a community platform; PostgreSQL also supplies full-text search, JSON, notifications, and extensions without forcing multiple services on small deployments | MySQL/MariaDB are reasonable relational choices but offer a less cohesive fit for the planned search and event patterns; SQLite is useful for tests and tiny tools, not the primary multi-process database |
| Database access and migrations | Drizzle ORM 0.45 plus `pg`; reviewed SQL migrations generated by Drizzle Kit | SQL-shaped queries, typed schema access, a small runtime, PostgreSQL support, and migration files that can be reviewed and promoted independently | Prisma is mature and productive but adds generated-client/runtime conventions; Kysely is an excellent lower-level MIT query builder, but Drizzle gives the initial team a direct schema-to-migration workflow |
| Authentication and sessions | Better Auth is the candidate for the first auth task; use database-backed opaque sessions and secure cookies | MIT, TypeScript-first, self-hosted, framework-agnostic, and extensible. Keeping auth in the API boundary avoids tying identity to the web renderer | Auth.js is a valid choice when auth is owned by a Next.js app; Keycloak is powerful for an external identity server but is excessive for the default small install; Lucia is not selected because its original project is no longer the maintained default |
| Boundary validation | TypeBox 1.x with `@fastify/type-provider-typebox` | One schema supplies runtime validation, handler types, and Fastify response serialization. Validation stays at every HTTP, job, upload, and integration boundary | Zod is an excellent MIT alternative with broad ecosystem support, but the native JSON Schema/Fastify path is the simpler and faster fit here |
| Tests | Vitest 5 for unit and service/in-process HTTP tests; Playwright for browser E2E once the first interactive UI exists | Vitest is fast and TypeScript-friendly; Fastify injection tests exercise routes without a network; Playwright covers real browser accessibility and navigation across Chromium, Firefox, and WebKit | Jest is mature but duplicates more of the Vite-era toolchain; browser tests are not added before there is a real product flow to test |
| Search | PostgreSQL full-text search first; keep a search-provider boundary for a later external index | Zero extra service for small self-hosted installs, transactional source data, GIN indexes, and a straightforward migration path | Meilisearch is the preferred external index if typo tolerance, facets, or hybrid/semantic search outgrow PostgreSQL; Typesense is also viable. Elasticsearch/OpenSearch is reserved for a demonstrated need because its operational cost is higher |
| File storage | S3-compatible object-storage boundary; use an S3 client in the application and document SeaweedFS as the permissive self-hosted option | Object storage separates large/untrusted bytes from the relational database and works with local or hosted S3 endpoints. SeaweedFS is mature, Apache-2.0, and can start small before scaling | MinIO has historical adoption but its current community distribution/licensing and maintenance direction require a separate legal/maintenance review; Garage is a capable AGPL option but has a smaller ecosystem; local disk is development-only, not a scale contract |
| Realtime | Server-Sent Events for one-way live updates, backed by an outbox/read model; PostgreSQL `LISTEN/NOTIFY` is only a wake-up signal | SSE is browser-native, reconnectable, HTTP-friendly, and sufficient for live thread/notification updates. The durable event record remains in PostgreSQL | WebSockets via `@fastify/websocket` are reserved for genuinely bidirectional interactions. Valkey pub/sub or streams can be introduced when database notifications are no longer sufficient; `NOTIFY` is not durable and must not be the only event record |
| Background jobs | PostgreSQL-backed pg-boss when the first durable asynchronous task is needed; a separate worker process consumes jobs | Reuses PostgreSQL, supports retries, scheduling, backpressure, and transactional enqueueing without making Redis a prerequisite for every install | BullMQ plus Valkey is the scale-out option for very high queue throughput or independently operated queue infrastructure; do not add either before workload evidence exists |
| Deployment | Node standalone web output plus a separate API container/process, PostgreSQL, and a reverse proxy; Docker Compose is the first self-hosting shape, Kubernetes is an optional later target | One small deployment is understandable and portable; web/API workers and database can later scale independently. Caddy or another standard reverse proxy terminates HTTPS and routes `/api` without browser code calling localhost | No provider-specific SDK or serverless-only runtime in the core; Kubernetes is not a prerequisite for a small installation |
| Observability | Structured Pino logs now; OpenTelemetry API/SDK when cross-process traces or metrics are needed | Fastify already uses Pino, so logs are useful without another service. OpenTelemetry keeps exporters replaceable when the system becomes distributed | Do not add a hosted monitoring vendor or a full telemetry stack to the foundation |

The web and API are separate deployable boundaries, not separate microservices for every domain. Domain/application code remains in the API process until scale or ownership gives a specific reason to split it. The web process never connects directly to PostgreSQL.

## Repository layout

```text
apps/
  api/       Fastify HTTP boundary, operational endpoints, and future vertical slices
  web/       Next.js rendering boundary and browser UI
packages/
  db/        PostgreSQL client and migration configuration; no domain tables yet
docs/        Short decisions and operational conventions
```

Add a package only when two consumers need a stable shared contract. Do not create empty packages for anticipated plugins, providers, or domains. A future feature should keep its route/schema/application/data/UI code close together rather than spreading a small change across generic layers.

## TypeScript and code quality

- All packages use strict TypeScript, ESM, `noUncheckedIndexedAccess`, exact optional properties, and no unused locals or parameters.
- `tsconfig.base.json` contains shared safety settings. Runtime packages choose their own module/bundler settings explicitly.
- Biome is the single formatter/linter. Formatting and linting run from the workspace root; generated output, Next.js's generated `next-env.d.ts`, and lockfiles are excluded.
- Use named exports for application modules. Keep side effects at process entrypoints (`server.ts`, workers, and migration commands).
- Do not add tutorial prose, speculative abstractions, or comments that merely repeat the code. Comments should explain a non-obvious constraint or security decision.
- Every behavior change needs the smallest useful test at the boundary it changes. Do not write tests for unimplemented product behavior.

## Configuration and secrets

- `.env.example` documents names and safe local defaults; `.env` and all other environment files are ignored.
- Read environment variables at process/configuration edges, validate them, and pass typed values inward. Do not scatter `process.env` reads through domain code.
- Only explicitly public web values may use a `NEXT_PUBLIC_` prefix. Database URLs, signing keys, cookie secrets, storage credentials, and internal service URLs never do.
- Production secrets come from the deployment environment or a secret manager, not the repository or image. Configuration failures should stop startup rather than silently selecting insecure defaults.

## HTTP and error conventions

- Public application endpoints use `/api/v1/...`; operational health endpoints are outside the product API namespace.
- JSON request and response shapes are versioned at the boundary and described by TypeBox schemas. Response schemas are mandatory for new routes.
- Use resource-oriented HTTP methods and status codes. Use cursor pagination for potentially large collections; never make clients depend on database offset behavior.
- Dates are UTC ISO 8601 strings at the HTTP boundary. IDs are opaque to clients.
- Errors use `application/problem+json` with a stable machine-readable code, status, request ID, and safe detail. Validation errors identify fields without echoing secrets. Unexpected errors are logged server-side and return a generic message.
- The web talks to the API through relative URLs and the server-side proxy/reverse proxy. Browser code must not use `localhost` or `127.0.0.1` as an API address.

## Security, accessibility, and discoverability

- Validate and bound every untrusted input, including query strings, headers, JSON, multipart metadata, webhook payloads, and job data. Use parameterized queries and least-privilege database credentials.
- The API enables security headers, a 1 MiB default JSON body limit, and structured request logging. Redact authorization, cookies, credentials, and token-like fields. Do not log message bodies or personal data by default.
- The future cookie session policy is `HttpOnly`, `Secure` in production, an explicit `SameSite` value, short-lived/rotated credentials where appropriate, origin/CSRF protection for state-changing browser requests, and revocation in the database. Rate limits and abuse controls are part of the auth and posting work, not an afterthought.
- Uploaded bytes will be treated as hostile: size/type limits, content sniffing protection, non-executable storage keys, malware-scanning hooks where appropriate, and authorization checks on every read.
- Public pages should use semantic HTML, keyboard-visible focus, labels, useful heading order, reduced-motion respect, and server-rendered text. The SEO/AI-search baseline is honest visible content plus canonical URLs, metadata, robots/sitemap controls, JSON-LD where it describes the page, stable links, and fast HTML—not hidden keyword or generated-content tricks.

## Database and migration rules

- PostgreSQL is the source of truth. `packages/db` owns connection construction and Drizzle Kit configuration; the API owns transaction boundaries and domain operations.
- Migration files are immutable, reviewed SQL artifacts. Generate them from the typed schema, inspect the SQL, and apply them in release order. `drizzle-kit push` is for local experimentation only, never production.
- Use expand/contract changes for deployed systems: add compatible structures, deploy readers/writers, backfill in a bounded job, then remove old structures in a later migration.
- Keep migrations free of demo data. Separate any intentional operational data task from schema migration review.
- Backups, restore drills, retention, and migration rollback plans are deployment requirements before production data exists.

## Licensing

The repository is AGPL-3.0-only. The selected direct software dependencies use MIT, Apache-2.0, or BSD-family licenses that are compatible with distributing an AGPL application when their notices and license terms are preserved. Apache-2.0 patent and notice terms still need to be retained. A dependency is not accepted solely because its source is visible: source-available, field-of-use-restricted, or network-copyleft infrastructure needs a separate legal decision.

The foundation intentionally does not install the deferred auth, search, object-storage, realtime, queue, or telemetry clients. Adding a dependency requires checking its direct and transitive licenses, maintenance/security status, Node support, bundle/runtime cost, and whether an existing component already solves the need. The current lockfile review also found LGPL-3.0-or-later libvips, MPL-2.0 Lightning CSS, and CC-BY-4.0 browser-compatibility data in transitive packages; their notices/attribution must remain available in redistributed artifacts.
